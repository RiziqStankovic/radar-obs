## Answer

### Decision

Use these Contrib receivers at OTel/Contrib `v0.158.0`:

- **Cluster-wide:** `k8sclusterreceiver` (`k8s_cluster`). It is explicitly cluster-scoped and its upstream README says only one instance should monitor a cluster. Enable its `k8s_leader_elector` reference so only one Radar Agent DaemonSet pod scrapes cluster metrics/events. Do not use `k8sobjectsreceiver` for the cluster metrics capability; it is primarily a generic Kubernetes object-to-logs receiver and also requires leader election plus storage when run in more than one pod.
- **Host resource metrics:** `hostmetricsreceiver` (`hostmetrics`), already selected in `radar-agent/builder-config.yaml:11-23` and configured in `radar-agent/config/collector.yaml:12-23` and the Helm-rendered `radar-agent-chart/templates/configmap.yaml:36-49`. It is node-local and must run on every DaemonSet pod. The host filesystem mount/root path in `radar-agent-chart/templates/daemonset.yaml:77-83,103-110` is required for host rather than container metrics.
- **Node/pod/container resource metrics:** `kubeletstatsreceiver` (`kubeletstats`). It is the appropriate node-local Kubernetes resource receiver, scraping the node kubelet at `10250`; the existing reference config is `radar-agent/config/otel-config.yaml:26-34,61-64`. Keep it on every DaemonSet pod and use the downward-API node identity; do not leader-elect it, or one node's metrics would be missing.
- **Database resource metrics:** add `postgresqlreceiver` and `mysqlreceiver` only for matching configured targets. Their v0.158 upstream docs require database credentials/privileges, not Kubernetes RBAC. PostgreSQL monitoring requires `SELECT` on `pg_stat_database`; MySQL metrics require `SHOW GLOBAL STATUS`, with `SELECT` on `performance_schema.*` for query samples. These receivers do not provide Kubernetes leader election, so the database capability must be enabled only by the existing logical capability owner (`agent.collectors.database.ownership: leader`) and its `radar-database-collector` Lease. Keep PostgreSQL QAN as the planned custom receiver/exporter path; the built-in PostgreSQL receiver is suitable for resource metrics, not a replacement for the QAN contract.

### RBAC and ownership

- The current chart already has the baseline ClusterRole needed for this design in `radar-agent-chart/templates/rbac.yaml:8-26`: read/watch access to pods, nodes, namespaces, services/endpoints, workload objects, jobs/events; `get` on `nodes/stats`; and Lease `get/list/watch/create/update/patch`.
- `kubeletstats` needs `get` on `nodes/stats`; the current rule is sufficient for the configured `node`, `pod`, and `container` metric groups. Add `nodes/pods` only if enabling its extra metadata or request/limit-utilization options; add PVC/PV `get` only if enabling its `k8s_api_config` volume metadata. Source: upstream `receiver/kubeletstatsreceiver/README.md` at tag `v0.158.0`.
- `k8sclusterreceiver` needs the upstream cluster-scoped read/list/watch set: core `events`, `namespaces`, `namespaces/status`, `nodes`, `nodes/spec`, `persistentvolumes`, `persistentvolumeclaims`, `pods`, `pods/status`, `replicationcontrollers`, `replicationcontrollers/status`, `resourcequotas`, `services`; `discovery.k8s.io/endpointslices`; apps workload resources; batch jobs/cronjobs; autoscaling HPAs. Add `extensions` and `quota.openshift.io` rules only for the relevant cluster. Endpoint metrics specifically add `endpointslices`. Source: upstream `receiver/k8sclusterreceiver/README.md` at `v0.158.0`.
- Leader election must be capability-specific, not global: cluster uses the upstream `k8sleaderelector` extension and `radar-cluster-collector` Lease; database and QAN use the existing configured `radar-database-collector` and `radar-qan-collector` ownership leases. A standby DaemonSet pod must report status but not poll or export for that capability. The existing Lease verbs are sufficient for the Kubernetes client-side election; keep the ClusterRoleBinding in `radar-agent-chart/templates/rbac.yaml:28-41`.

### Build and routing facts

- `radar-agent/builder-config.yaml:7-23` pins OCB and Contrib to `0.158.0`, but currently builds only `otlpreceiver`, `hostmetricsreceiver`, batch, memory limiter, OTLP HTTP exporter, and health check. The module cache currently contains `hostmetricsreceiver@v0.158.0` (for example `C:/Users/Riziq Maulana/go/pkg/mod/github.com/open-telemetry/opentelemetry-collector-contrib/receiver/hostmetricsreceiver@v0.158.0`), but no cached `k8sclusterreceiver`, `kubeletstatsreceiver`, `postgresqlreceiver`, or `mysqlreceiver` directories. Treat upstream `v0.158.0` component documentation/source as the availability reference and add each selected receiver/extension explicitly to OCB before implementation.
- The Helm-rendered production pipeline sends OTLP traces, metrics, and logs through `otlphttp/radar-gateway` to `${RADAR_GATEWAY_OTLP_ENDPOINT}` (`radar-agent-chart/templates/configmap.yaml:58-87`). The default gateway value is `http://radar-gateway:4318` (`radar-agent-chart/values.yaml:16-24`); preserve this existing HTTP OTLP endpoint for all built-in receiver signals. The gateway collector accepts OTLP and persists through its ClickHouse exporter (`radar-gateway/builder-config.yaml:11-19`).
- Do not send QAN as OTLP metrics/logs. Preserve the map contract: the custom QAN exporter posts to Go gateway `POST /v1/qan/collect`; ClickHouse credentials remain gateway-owned. Database metrics from `postgresqlreceiver`/`mysqlreceiver` do use the ordinary OTLP metrics pipeline and the gateway endpoint.
